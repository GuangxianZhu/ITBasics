# 别墅机器人助理 · 第一阶段方案

> 目标：在 Godot 版别墅里放一个机器人助理。你用**语音**叫它**去拿东西**，或者问它**家里的情况**，它用语音回答。
> 范围：只用游戏里的信息；全部在本机跑（RTX 5090 + Ollama），不联网。
> 状态：方案，还没写代码。

---

## 1. 一句话原理

**大模型只做"听懂 + 决定"，不碰动作。** 大模型把你的话翻译成一条结构化指令（比如 `{"action":"fetch","target":"可拿_沙滩球"}`），Godot 里写死的代码负责寻路、抓取、递给你。

为什么这样分：
- 大模型擅长理解"把那个球给我拿过来""楼上有人开着灯吗"这种说法多变的话，但它控制不了每一帧的移动，也保证不了不穿墙。
- 寻路、抓取是确定性的老问题，用 Godot 自带的导航系统就能稳定做好。
- 这样大模型说错了最多是"做错一件事"，不会让机器人卡进墙里或飞出地图。

**依赖的假设**：你说的每句话能对应到一个有限的动作清单里。如果你想让它做清单外的事（比如"跳个舞"），它只能回答"我还不会"——这是故意的。

## 3. 机器人能做的事（第一阶段的动作清单）

| 指令 | 例句 | Godot 里怎么执行 |
|---|---|---|
| `fetch` 取东西 | "把沙滩球拿给我""帮我拿个椰子" | 寻路到物品 → 吸起来 → 寻路回到你面前 → 递到你手边 |
| `report` 汇报 | "二楼灯开着吗""杯子都在哪""现在是白天还是晚上" | 不动，直接说 |
| `come` 过来 | "过来""到我这儿来" | 寻路到你身边 |
| `goto` 去某处 | "去厨房" | 寻路到房间中心 |
| `stop` 停下 | "停""算了" | 放下手里的东西，原地待命 |
| `clarify` 反问 | "拿那个"（指代不清时） | 不动，问你"你是说沙滩球还是椰子？" |

**能拿的东西**就是现在场景里能抓的那些：沙滩球 ×2、椰子、杯子（`可拿_*`）。以后加新物品，只要按 `可拿_名字` 命名，机器人自动就能拿。

## 4. 关键设计

### 4.1 世界快照：让大模型"只能"用游戏里的信息

每次你说话时，Godot 生成一份当前状态的 JSON，跟你的话一起发给大模型：

```json
{
  "时间": "黄昏",
  "你在": "一楼客厅",
  "机器人在": "一楼厨房",
  "物品": [
    {"id": "可拿_沙滩球",  "名称": "沙滩球", "房间": "泳池", "离你": 9.2},
    {"id": "可拿_椰子_0",  "名称": "椰子",   "房间": "外廊", "离你": 4.1}
  ],
  "设备": {"一楼灯": true, "二楼灯": false, "电视": false, "冰箱门": "关", "烧烤炉": "灭", "KTV": false}
}
```

- **房间判断**：在代码里给每个房间写一个包围盒（客厅、厨房、餐厅、电视角、卫生间、卧室、娱乐室、阳台、外廊、泳池、步道、凉亭、草坪），物品坐标落在哪个盒子里就是哪个房间。
- **为什么要这样**：大模型没见过你的别墅，不给它数据它就会编。给它一份清单，并在提示词里要求"只能根据这份清单回答，清单里没有就说不知道"。
- **会失效的地方**：大模型仍然**可能**编（概率小但不为零）。所以数字类问题（"有几个杯子"）最好由代码先数好放进快照，让它照读，而不是让它自己数。

### 4.2 结构化输出：让大模型的回答一定能被程序读懂

用 Ollama 的 **structured outputs**：请求时在 `format` 里传一个 JSON Schema，模型的输出会被约束成这个格式（[Ollama 文档](https://lzw.me/docs/ollama/en/capabilities/structured-outputs.html)）。

```json
{
  "action": "fetch | report | come | goto | stop | clarify",
  "target": "物品 id 或房间名，没有就是空",
  "say": "机器人要说的话（一两句）"
}
```

- 文档建议**同时把 Schema 写进提示词**、温度设为 0，结果更稳。
- **Godot 端还要再校验一次**：`target` 必须是快照里真实存在的 id，否则当作 `clarify` 处理。格式约束只保证"形状对"，不保证"内容对"。
- 指代不清的规则写在代码里，不交给模型：同名物品有多个时，默认拿**离你最近**的那个。

### 4.3 移动：Godot 导航网格

- 启动时用 `NavigationRegion3D` 从房子的**静态碰撞体**烘焙一张导航网格（后台线程烘焙，不卡画面）。机器人身上挂 `NavigationAgent3D`，给它目标点就自己找路。
- 参数按现有尺寸定：楼梯每级 17.8cm、宽 1.1m → `agent_max_climb` 设 0.25m，`agent_radius` 设 0.3m 左右。
- **推拉门**：烘焙时把门的碰撞体排除掉（当作能通过），机器人走到门前 1m 时自动调用门的开门函数（现成的 `interact`），过去后不关。
- **可能失效**：家具之间太窄、斜坡太陡、泳池台阶处导航网格断开。到时在桌面模式里打开导航网格显示，哪里断了一眼就能看到。

### 4.4 抓取与递交

复用现有的抓取系统（`grabbable` 组里的 `RigidBody3D`）：
1. 机器人到物品 0.6m 内 → 把物品设为冻结、挂到机器人"手"上（和你隔空抓东西是一个道理）。
2. 回到你面前，把东西举到你**惯用手**前方约 40cm 处。
3. 你按握把抓住它的那一刻，机器人松手（在 `player.gd` 的抓取函数里加一个通知）。
4. 10 秒没人接，就轻轻放到你脚边地上。

## 5. 机器人的外形：三个方向

| 方向 | 好处 | 代价 |
|---|---|---|
| **A. 悬浮的圆球小机器人**（带一个光圈"手"）⭐推荐 | 不用走路动画、不用腿；"吸住东西"看起来很自然；全部能用代码拼出来，跟别墅其他部分一样不需要外部素材 | 不太像"管家" |
| B. 轮式机器人（像扫地机器人上面加个躯干） | 有真实感，在地面走 | 上下楼梯要做特殊处理（升降、或者干脆不上二楼） |
| C. 人形机器人 | 最有"管家"感 | 要走路动画、手部动作对准物品，工作量是 A 的好几倍 |

推荐 A 的原因：第一阶段的难点在"听懂 + 找路 + 递东西"，外形越简单越能把精力放在这上面。以后可以换模型，逻辑不用改。

## 6. 三个技术选择

### 6.1 语音转文字

| 方案 | 说明 |
|---|---|
| **faster-whisper（large-v3-turbo，GPU）** ⭐推荐，主流做法 | 中文识别准确度好，5090 上一句话的识别时间很短 |
| Whisper 小模型 | 更快，但中文口语容易错字 |

### 6.2 理解 + 决定（Ollama 模型）

- 用你 Ollama 里已经有的、中文好的模型，比如 Qwen3 系列 8B~14B 级别。具体型号到时以你 `ollama list` 里的为准。
- 如果是会"思考"的模型，请求时**关掉思考**：这个任务很简单，思考只会多等几秒。
- 模型越大越懂"那个、这个"一类的指代，但每句话要多等一点。先用中等的，觉得笨再换大的。

### 6.3 文字转语音

| 方案 | 好处 | 代价 |
|---|---|---|
| **A. Godot 自带 TTS（调用 Windows 系统语音）** 先用这个 | 零安装，一行代码 | 声音比较机械；声音不是从机器人身上发出的（不是 3D 空间音） |
| B. 本地神经网络 TTS（Python 服务生成 WAV） | 声音自然；Godot 用 `AudioStreamPlayer3D` 播放，声音真的从机器人那里传来 | 要多装一个模型，多等不到一秒 |

建议：第一步先用 A 把整条链路跑通，第二步换 B。

## 7. 按键

现有按键里 A/X、B/Y、扳机、握把、左摇杆按下都占用了。

- **VR**：按住**右摇杆按下**说话，松开就发送（对讲机模式）。
- **桌面模式**：按住 **V** 说话；另外按 **回车**可以直接打字发指令，方便不戴头显时调试。

为什么不用"一直听、自动判断你在说话"：别墅里有海浪、收音机、KTV 的声音，自动判断很容易误触发。对讲机模式最可靠。

## 8. 一键启动

按惯例做成 Windows 一键启动：

- **新增 `启动_机器人服务.bat`**：
  1. `git pull --ff-only origin main` 检查更新（离线就跳过）
  2. 用 uv 建一个独立的 Python 环境，装 faster-whisper 等依赖（第一次运行时，之后跳过）
  3. 检查 Ollama 是否在运行、需要的模型是否已下载，没下载就 `ollama pull`
  4. 启动机器人服务（只监听 127.0.0.1，外部访问不了）
- **改 `启动_Godot版.bat`**：如果发现机器人服务没在运行，就自动在另一个窗口启动它。
- **没有服务时**：别墅照常能玩，只是机器人头上显示"离线"，不会报错。

## 9. 开发步骤

| 步骤 | 内容 | 怎么验证 |
|---|---|---|
| M0 | 放一个圆球机器人；烘焙导航网格；按键让它跟着你 | 桌面模式里看它上下楼梯、穿过推拉门 |
| M1 | 打字 → Ollama → JSON 指令 → 机器人执行（先不接语音） | 打"把沙滩球拿给我"，看它拿回来 |
| M2 | 世界快照 + 汇报 | 问"二楼灯开着吗"，开关灯后再问，答案要跟着变 |
| M3 | 接语音输入（faster-whisper） | 桌面模式用电脑麦克风说话 |
| M4 | 语音输出（先系统语音，再换 3D 神经网络语音） | 听声音是不是从机器人那边来 |
| M5 | VR 实测 | 戴头显，用 Quest 麦克风完整走一遍 |

每一步都加进现有的自动测试（`--walktest`）：用**固定的假回答**代替大模型，测"拿球回来""开门过去""问灯状态"，这样不开 Ollama 也能测。

## 10. 哪些是确定的，哪些还要验证

| 结论 | 证据强度 |
|---|---|
| "大模型出指令、传统代码执行"的分工 | **公认做法**，游戏和机器人领域都这么做 |
| Ollama 能用 JSON Schema 约束输出格式 | **官方功能**，有文档 |
| Godot 导航网格能运行时从碰撞体烘焙 | **官方功能** |
| Virtual Desktop 能把 Quest 麦克风变成电脑上的麦克风设备 | **社区文档说可以**（[VD FAQ](https://reddit.birdcat.cafe/r/OculusQuest/wiki/faq/virtualdesktop)，叫 "Virtual Desktop Microphone"，默认开启）；你的电脑上还没确认 |
| 一句话从说完到机器人开口约 2~3 秒 | **我的推测**：识别 + 模型 + 语音合成各零点几秒到一秒多。实际要测。为了不让你干等，机器人收到指令会先马上说一声"好的" |
| 中等大小的本地模型足够听懂中文口语指令 | **推测**，任务简单，应该够；指代复杂时可能要换大模型 |
| 导航网格在泳池台阶、阳台门口这些地方是通的 | **未知**，要在 M0 实际看 |
