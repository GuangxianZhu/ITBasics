# 双向通信改造方案（IO 温水器 → 全串口温水器，清洗机软件不改）

## 1. 总体思路

清洗机软件和原来的 IO 一个都不动，中间加一台三菱 PLC 当「翻译」：

```
清洗机 ──DO/AO──▶ PLC ──RS-485──▶ 新温水器
清洗机 ◀──DI───── PLC ◀──RS-485── 新温水器
```

对清洗机来说，PLC 就是「原来那台 IO 温水器」。

## 2. 信号映射表

### 清洗机 → 温水器（PLC 输入 → 串口命令）

| 原 IO | PLC 侧 | 串口动作 | 注意 |
|---|---|---|---|
| 远程 | DI | 写 远程/本地 | 电平 |
| 在线 | DI | 开始/停止通信，许可 | 电平 |
| 通水 | DI | 写 通水（或只做联锁） | 看新温水器有没有对应命令 |
| 加热 | DI | 写 运转/停止 | 电平 |
| 温度设定 | AI（4-20mA） | 写 SV | 换算、滤波、死区、限频；<3.6mA 判 AD 断线 |
| 复位 | DI | 上升沿：清 PLC 侧锁存 + 发温水器复位命令 | 和原 IO 复位一样的用法 |

### 温水器 → 清洗机（串口状态 → PLC 输出）

| 原 IO | 来源 | 通信异常时 |
|---|---|---|
| 温度 Ready | 状态位（或 \|PV−SV\|<带宽 自己算） | 强制 OFF |
| 过热 | 状态位 | 保持最后值 |
| 漏水 | 状态位 | 保持最后值 |
| 轻故障 | 状态位 | 保持最后值 |
| 重故障 | 温水器重故障 **OR 通信异常** OR PLC 自诊断异常 | 强制 ON |

通信故障并入「重故障」→ 清洗机软件不用改，按原来重故障的处理走。

## 3. 和上一版模拟器最大的不同：电平语义

原来是 IO：清洗机一直保持「加热=ON」，温水器一直看得到。
串口命令是一次性的，所以 PLC 不能只在边沿发一次，要做**期望状态对账**：

- 期望状态 = 清洗机给的 DI/AI（远程、运转、SV…）
- 实际状态 = 轮询读回的状态
- 两者不一致 → 重发写命令（限次数、限频）
- 温水器重启/断电恢复后状态丢了，也能自动补回来 → 这就是「电平」的效果

例外：温水器自己因故障停机时不要硬拉起来，等故障消失再对账。

## 4. 通信故障判定

- 连续 N 次（例 3 次）超时/校验错 → 通信异常
- 或 T 秒（例 2s）内没有一次有效响应 → 通信异常
- 异常时：重故障 ON、Ready OFF
- 解除：**和原 IO 重故障一样，锁存，等清洗机给「复位」**
  - 复位上升沿时通信正常 → 清除通信异常，同时给温水器发复位命令
  - 复位时通信仍然不通 → 不清除，重故障保持 ON
  - 通信恢复了但没人按复位 → 重故障继续 ON（不自动解除，和 IO 行为一致）
- AD 断线（<3.6mA）：不发新 SV，保持上一次的值，输出轻故障（待定）

## 5. 确认状态

| 项目 | 状态 |
|---|---|
| 复位信号 | 有（清洗机 → 温水器） ✓ |
| 温度设定 AD | 电流信号 ✓（量程对应多少 ℃ 待查） |
| 故障信号极性（1=故障 / 0=故障） | 待查。PLC 断电时输出全 0，如果原来是 1=故障，PLC 坏了会被当成正常 |
| 新温水器通信看门狗 | 不清楚 → 查手册。没有的话：通信断了温水器可能一直按最后的命令加热，只能靠它自己的保护和急停 |
| 硬线 | 只有急停 ✓；漏水时温水器自己停机 |
| 清洗机等 Ready 的超时 | 待查（串口有轮询延迟） |

## 6. 自定义协议框架（分 4 层，拿到手册填表即可）

| 层 | 内容 | 拿到手册要填的 |
|---|---|---|
| ① 链路设置 | 波特率、数据位、校验、停止位、站号 | 通信规格那一页 |
| ② 帧编解码 Codec | 帧头/帧尾、字段顺序、ASCII/二进制、校验方式和范围 | 帧格式、BCC/SUM/CRC 计算范围 |
| ③ 命令表 | 每条命令：代码、请求数据格式、响应格式、含义 | 命令一览、参数号一览 |
| ④ 点表/映射 | PLC IO ↔ 协议数据点，换算、通信异常时的策略 | 本方案第 2 节的表 |

事务层（轮询调度、超时、重发、半双工）是固定的，不用随协议改。

### 和 Modbus 的关系

原理基本一样：都是**主从、一问一答、带站号、带命令码、带校验、主站轮询**。
Modbus RTU 可以当成这个框架的一个「实例」：二进制 + CRC16 + 靠 3.5 字符静默分帧 + 寄存器模型。

主要差别：

| | 厂家自有协议（常见） | Modbus RTU |
|---|---|---|
| 编码 | ASCII 居多，能直接看懂 | 二进制 |
| 分帧 | STX/ETX 或 CR/LF | 3.5 字符静默时间 |
| 校验 | BCC(XOR) / SUM / 无 | CRC16 |
| 数据模型 | 命令式或参数号式 | 统一寄存器/线圈地址 |
| 数值 | 十进制字符串、小数点规则各家不同 | 16 位整数 |

### 先定的规则（虚构协议 v2，参数号式，接近日本厂家常见风格）

```
请求: STX | 站号(2) | R/W(1) | 参数号(3) | [数据(n)] | ETX | BCC
响应: STX | 站号(2) | R/W(1) | 参数号(3) | ACK/NAK(1) | [数据 或 错误码] | ETX | BCC
BCC = 站号 ~ ETX 的 XOR，全 ASCII
```

参数号（相当于 Modbus 的寄存器地址）：

| 参数号 | R/W | 含义 |
|---|---|---|
| 001 | W | 远程/本地 |
| 002 | W | 运转/停止 |
| 003 | W | 通水指令 |
| 010 | R/W | SV（×0.1℃） |
| 100 | R | PV（×0.1℃） |
| 101 | R | 状态字（Ready/运转/远程…） |
| 102 | R | 报警字（过热/漏水/轻故障/重故障…） |

这样换真协议时：codec 改帧格式，命令表改参数号，点表基本不动。

## 7. 模拟器改法

- 左：清洗机侧（DO/AO 给 PLC、DI 从 PLC 读），沿用原来的 IO 名
- 中：时序图增加「AD 温度设定」模拟量行、「通信异常」行
- 新用例：温水器重启后状态自动补回、AD 抖动不刷屏、断线→重故障→恢复、Ready 延迟
- 协议拆成 `codec / command_table / point_map` 三个文件，引擎不动
